# 0.3.0 plan: Tensorseed Desktop

Status: approved; decisions recorded in section 7. Milestones M3.0, M3.1,
and M3.2 are in progress. This expands SPEC section 19 into a build plan. Where this
document and the SPEC disagree, the SPEC wins until the SPEC is revised.

## 1. Goal

A desktop app that lets someone who never opens a terminal browse and verify
Tensorseed catalogs, pull models and datasets with visible progress, and seed
them back, while sharing one config, one library, and one seeder with the
`tensorseed` CLI on the same machine.

Non goals for 0.3.0: publishing or signing catalogs, harvesting, running the
official seeder (that stays a systemd service), non Hugging Face sources,
mobile.

## 2. Recommended stack: Tauri 2

**Recommendation:** Tauri 2, a new `desktop/` app in this repository, with
the explorer's Svelte 5 + TailwindCSS + DaisyUI UI reused and the Rust crates
called natively from Tauri commands.

Why it fits this codebase:

- The UI already exists. `explorer/` is a Svelte 5 + Vite app with a small
  data layer (`explorer/src/lib/catalog.ts`) around a `CatalogVerifier`
  from `tensorseed-wasm`. In Desktop that same component tree runs in the
  system webview, and the data layer switches from WASM plus `fetch` to
  Tauri `invoke` calls into the native crates.
- The backend is already Rust. `tensorseed-fetch` (resumable verified
  downloads), `tensorseed-torrent` (librqbit engine with `Progress` and
  `EngineStats`), `tensorseed-catalog`, `tensorseed-verify`, and
  `tensorseed-hf` link directly into the Tauri process. No sidecar
  protocol is needed for core features.
- Small installers (system webview, no bundled browser), a built-in tray
  API, single instance, autostart, deep links, and an updater whose
  signatures use the minisign format we already use.
- The Tauri bundler produces .deb, .rpm, AppImage, MSI (WiX), NSIS, .app,
  and .dmg from one config.

### Alternatives considered

| Option | For | Against |
| --- | --- | --- |
| **Tauri 2** (recommended) | Reuses the Svelte UI and the Rust crates as is; small bundles; tray, updater, single instance built in; Rust end to end | System webviews differ (WebKitGTK on Linux, WebView2 on Windows, WKWebView on macOS), so the UI needs testing on each; Linux needs glibc and webkit2gtk-4.1, so no static musl build |
| Electron | One Chromium everywhere, mature tooling, huge ecosystem | 100 MB or more per install, a Node main process, and the Rust crates would need a sidecar or N-API bindings; two runtimes to secure and patch |
| Dioxus (desktop) | Pure Rust, webview based like Tauri | UI rewritten in RSX, so the explorer is not reused; younger ecosystem for tray and packaging |
| egui / iced / Slint | Native rendering, no webview differences, small binaries | Full UI rewrite, a second design system to maintain, weaker text and accessibility story than the web UI (Slint also has its own licensing terms to check) |
| Local web UI served by `tensorseed serve` | No new app at all; works on headless hosts | No tray, no native notifications or file dialogs, a browser tab is easy to lose; still useful later as a remote view |

Tauri keeps the most existing code, so it is the lowest risk path to a
first release. Electron is the fallback only if webview differences turn
out to be unmanageable. Extending the explorer's Playwright suite to a
WebKit project early in M3.1 will show that before much Desktop code
exists.

## 3. Architecture

```
desktop/
  src-tauri/        Rust: Tauri app, commands, tray, background tasks
  src/              Svelte 5 front end (shared components from explorer/)
crates/
  tensorseed-app/   new: config, catalog sync, pull, seed, hf login as a
                    library (moved out of tensorseed-cli)
ui/                 shared Svelte 5 components (pnpm workspace package)
```

1. **Extract a library crate.** Most user facing logic lives in
   `tensorseed-cli` today (`config.rs`, `consumer.rs` for pull,
   `serve.rs`, `follow.rs`, `hf_auth.rs`, `torrents.rs`). Move the reusable
   parts into a new `tensorseed-app` crate with no clap and no printing,
   returning structured results and progress events. The CLI becomes a thin
   front end over it; behaviour and output stay the same, guarded by the
   existing CLI tests. This is the largest single task and should land
   first, in small steps.
2. **Share UI components.** Move the explorer's components and types into
   a shared package (`ui/` as a pnpm workspace package) used by both
   `explorer/` and `desktop/`. A small `CatalogSource` interface hides
   whether verification runs in WASM (explorer) or natively (desktop).
   The explorer keeps building and deploying unchanged.
3. **Tauri commands** wrap `tensorseed-app`: `catalogs_list`,
   `catalog_sync`, `entries_list`, `entry_show`, `pull_start`,
   `pull_cancel`, `seed_set`, `seed_pause`, `settings_get`,
   `settings_set`, `hf_status`, `hf_login`, `hf_logout`. Long tasks
   report progress through Tauri events (`pull://progress`,
   `seed://stats`).
4. **One seeder per machine.** SPEC 19 requires shared state with the CLI.
   Two engines on the same data would fight over the listen port, DHT
   state, and files. Plan: a lock file in the data directory. If a
   `tensorseed serve` is already running, Desktop attaches to it as a client
   (read its health endpoint now; add a small authenticated local control
   endpoint for pause, resume, and seed selection); otherwise Desktop runs
   the engine in process and takes the lock. `serve`, `list`, and `jobs`
   see the same SQLite job state either way.
5. **Security.** Tauri capabilities limited to the commands above; a strict
   CSP like the explorer's; no remote content loaded into the webview; the
   HF token stays in the existing token file (never sent to the front end),
   with OS keychain storage as an option to evaluate.

## 4. Feature scope for 0.3.0

Must have:

- **Browse and verify catalogs.** The explorer views (list, search, entry
  page, catalogs page, agreement across catalogs) backed by the native
  verifier, including the Chia anchor check and the `strict` / `warn` /
  `off` chain check from config. Add and remove subscribed catalogs, same
  as `tensorseed catalog add` / `remove`.
- **Pull with progress.** Start a pull from an entry page, with
  `--include` / `--exclude` style file selection, per file and total
  progress, source shown (swarm, Hub, HTTP mirror), pause, resume after
  restart, cancel, and a final verification result. Uses the same job state
  as `tensorseed jobs`.
- **Library.** Pulled revisions on disk, size, verification status,
  re-verify, open folder, delete.
- **Seeding controls.** Per revision seed on or off, global pause, upload
  rate limit, live peers and speeds from `EngineStats`, total uploaded.
- **Tray.** Status (idle, pulling, seeding, error), pause and resume all,
  open window, quit. Optional start at login (off by default).
- **Settings.** Data directory, listen port and UPnP, rate limits,
  catalogs, chain check mode, disk budget. Writes the same config file the
  CLI reads, preserving comments where possible.
- **Hugging Face login.** Status, paste token, log out, using the existing
  `hf login` token file and the existing lookup order (env, our file, the
  Hugging Face CLI token). The token is never displayed after saving.
- **`tensorseed gui`** in the CLI: open Desktop if installed, else print the
  download link (SPEC 19). No GUI libraries linked into the CLI.

- **Commercial serving marks.** Entry lists and entry pages show the
  `allowed` / `restricted` / `forbidden` / `unknown` badge from
  `tensorseed_core::commercial::assess` (the same table as the CLI and
  the explorer), with a filter and the "not legal advice" note. The list
  already carries it (`EntryView.commercial`).
- **Serve inference (CLI first, Desktop view later in 0.3.x).** The CLI
  ships `tensorseed serve-inference` in 0.3.0 (docs/SELL-INFERENCE.md).
  Everything except printing lives in `tensorseed_app::inference`
  (`verify_copy`, `license_gate`, `choose_runtime`, `LaunchPlan`,
  `wait_ready`, `ServedWeights`), so a Library "Serve" action can reuse it
  without new logic. The `ts.served-weights/0` record is unsigned; the
  signed weights statement is a later, separate design.

Should have, if time allows: native notifications on pull finished or
failed, deep links (`tensorseed://entry/model/<org>/<name>`) from the web
explorer's "open in Desktop" button.

Also must have (decided): the Tauri in app updater (section 5, Updater).

Later: remote view of a headless `serve`, publishing tools.

## 5. Platform packaging

Release targets for 0.3.0 are Linux and Windows. macOS is designed for but
not released in 0.3.0 (see "macOS: designed for, not released yet" below).

| Platform | Formats | Notes |
| --- | --- | --- |
| Linux x86_64 and aarch64 | .deb, .rpm, AppImage | glibc build against webkit2gtk-4.1 (floor: Ubuntu 22.04, Debian 12, Fedora 36). The .deb and .rpm bundle the CLI binary by default (decision 5); the 0.2.0 CLI packages stay GUI free. AppImage bundles the CLI binary. |
| Windows x86_64 (aarch64 later) | MSI (WiX) and NSIS | Both ship (decision 3). WebView2 bootstrapper included. MSI suits managed and per machine installs; NSIS gives per user installs without admin. Unsigned at first (decision 2). |
| macOS | not released in 0.3.0 | Code and config kept portable so a .app and .dmg can be added later without restructuring. |
| Flatpak (x86_64 and aarch64) | ships in 0.3.0 (decided) | App id `dev.tensorseed.desktop`. Permissions: network, a user chosen data directory through the file chooser portal plus a default under the app data dir, and the tray through the StatusNotifier portal. The listen port works inside the sandbox since Flatpak shares the host network. The in app updater is disabled in the Flatpak build; updates come from the Flatpak remote. |

Build machine: all release builds run on the Linux build host. Linux
packages build natively there. Windows installers are cross built from
Linux: NSIS through `makensis` and Tauri's documented Linux to Windows
cross build (`cargo-xwin` or the zig based toolchain already used for the
CLI), and the MSI through WiX. WiX v3 is Windows only, so the MSI step
either runs WiX under Wine on the build host or moves to a hosted Windows
runner; M3.6 picks one after a spike, and the NSIS installer is the
fallback if the MSI path is not ready. A smoke test on a real Windows
machine is still required before release.

### Designed for macOS, not released yet

macOS is not a 0.3.0 release target, and SPEC 19 is not changed to promise
it. To keep it cheap to add later:

- Platform specific code is behind `cfg(target_os = ...)` with a portable
  default; paths come from the `dirs` style helpers already used for XDG
  and `%APPDATA%`, which map to `~/Library/Application Support` on macOS.
- The Tauri config keeps a `bundle.macOS` section stubbed out, and the
  bundle id `dev.tensorseed.desktop` and `tensorseed://` scheme are valid
  on macOS as chosen.
- CI type checks (`cargo check --target aarch64-apple-darwin`) the
  library crates where the toolchain allows, so macOS breakage is caught
  early even without shipping.

Later work, when macOS becomes a release target:

- A macOS CLI and Desktop build. Tauri apps cannot be practically cross
  built from Linux, so this needs macOS hardware or a hosted macOS runner
  (for example a GitHub Actions `macos-14` runner, Apple silicon). The CLI
  alone may cross build with cargo-zigbuild and a macOS SDK; untested.
- Signing and notarization: an Apple Developer Program membership for
  Tuned Chaos (annual fee), a Developer ID Application certificate,
  hardened runtime, and `xcrun notarytool` notarization plus stapling.
  Unsigned development builds run only after the user overrides
  Gatekeeper, so they are fine for testing but not for release.
- A universal (`universal-apple-darwin`) or Apple silicon only .dmg, signed
  with minisign and listed in `SHA256SUMS` like every other artifact.

### Signing

- **Release artifacts:** keep the existing minisign release key and
  `SHA256SUMS.minisig` flow for every Desktop artifact, signed on the
  release machine as today.
- **Updater:** Tauri's updater verifies its own minisign format signature
  with a public key compiled into the app. A separate, new updater key
  (not the release key), generated and kept offline on the release machine
  the same way, so a compromise of one does not expose the other. The key
  is never generated on the build host. See "Updater" below.
- **Windows Authenticode:** 0.3.0 ships unsigned (decision 2). Users will
  see a Microsoft Defender SmartScreen prompt ("Windows protected your
  PC") on first run and must choose "More info" then "Run anyway"; the
  download page and release notes say so and point to the minisign and
  `SHA256SUMS` check as the integrity proof. Some browsers may also flag
  the download as uncommon. Later options: an OV or EV code signing
  certificate on a hardware token or cloud HSM, or Azure Trusted Signing.
- **Linux:** minisign plus checksums as today; optionally a signed apt and
  dnf repository later (SPEC defers this).

### Updater

The Tauri 2 updater plugin (`tauri-plugin-updater`) ships in 0.3.0.

- **Feed:** a static JSON file on tensorseed.dev, for example
  `https://tensorseed.dev/desktop/latest.json`, using Tauri's static
  `latest.json` format (version, notes, pub_date, and per platform `url`
  plus `signature`). Platform keys for 0.3.0: `linux-x86_64`,
  `linux-aarch64` (AppImage), and `windows-x86_64` (NSIS and MSI). The
  .deb and .rpm installs update through their package or the download page,
  not the in app updater, since Tauri only self updates AppImage on Linux.
- **Artifacts:** the update `url` points at the same signed release
  assets; each gets a `.sig` from the updater key. The feed is only
  published after the release is signed and uploaded.
- **Checks:** at most once a day and on demand from Settings; the user
  confirms before install. No telemetry: the request carries only what
  the HTTP client sends by default, and nothing is logged on our side
  beyond normal access logs.
- **Key generation (release machine, not the build host):** the release
  owner runs, in fish on the Arch based release machine:

  ```fish
  sudo pacman -S --needed nodejs pnpm
  mkdir -p ~/.tauri; chmod 700 ~/.tauri
  pnpm dlx @tauri-apps/cli@2 signer generate -w ~/.tauri/tensorseed-updater.key
  ```

  The command prompts for a password and writes
  `~/.tauri/tensorseed-updater.key` (private, never committed, backed up
  offline like the release key) and `~/.tauri/tensorseed-updater.key.pub`.
- **Public key placement:** the contents of the `.pub` file (one base64
  line) go in `desktop/src-tauri/tauri.conf.json` under
  `plugins.updater.pubkey`, and a copy is committed as
  `keys/tensorseed-updater.pub` with a note in `RELEASE-KEY.md`. Until
  then the config carries an empty placeholder and the updater is disabled
  at build time.
- **Signing updates (release machine):**

  ```fish
  pnpm dlx @tauri-apps/cli@2 signer sign -f ~/.tauri/tensorseed-updater.key <artifact>
  ```

  This writes `<artifact>.sig`, whose contents go in `latest.json`.

## 6. Milestones

1. **M3.0 Library extraction.** `tensorseed-app` crate, CLI ported onto it,
   all CLI tests green, no behaviour change. Progress callbacks added to pull
   and seed (may land with M3.3 and M3.4 if the move itself is large).
   Status: first pass landed. `tensorseed-app` now holds `config`,
   `serve_config`, `follow`, `backend`, `chain` (client check), `mirrors`
   (ranking), `torrents` (helpers), `pull` (pull record and manifest
   resolution), and `hf` (login state). Still in the CLI, to move with
   progress events in M3.3 and M3.4: the pull download pipeline and
   `verify` (`consumer.rs`), the `serve` daemon, the `seed` command, and
   `list` / `show` / `jobs` formatting. Publisher only code (harvest,
   catalog management, keys, the Chia write path) stays in the CLI, since
   publishing is a non goal for Desktop.
2. **M3.1 Shared UI.** `ui/` workspace package; explorer rebuilt on it and
   redeployed with no visible change; Playwright suite green.
   Status: first pass landed. `ui/` (`@tensorseed/ui`) holds `EntryList`,
   `StatusBanner`, `CommandBox`, `ThemeToggle`, the types, the format
   helpers, `theme.css`, and the `CatalogSource` interface
   (`ui/src/source.ts`). It is linked into each app with `link:../ui`
   rather than a root pnpm workspace, so the explorer keeps its own
   lockfile and deploy steps. The explorer builds on it with identical
   CSS apart from three unused badge classes, and its Playwright smoke
   test passes. Not redeployed yet (no visible change to ship). Still
   explorer only: `EntryPage` and `CatalogsPage` (they call the WASM data
   layer directly); they move once the explorer's `catalog.ts` implements
   `CatalogSource`.
3. **M3.2 Desktop shell.** Tauri 2 app, window plus tray, catalog browse
   and verify natively, settings read only, `tensorseed gui` stub.
   Status: scaffold landed. `desktop/` is a Tauri 2.12 app ("Tensorseed
   Desktop", `dev.tensorseed.desktop`, `tensorseed://` deep links through
   the deep link and single instance plugins). `desktop/src-tauri` is
   outside the root Cargo workspace (its own `[workspace]`, lockfile, and
   target; the root `Cargo.toml` excludes it) and needs Rust 1.90 for
   Tauri 2.12; the CLI crates keep 1.87. Commands so far:
   `catalogs_list` and `entries_list` (named `entries_list` as in item 3
   of section 3; `catalog_sync` is folded into it as a `sync` flag for
   now). Syncing goes through `tensorseed_app::backend::open_reader`, so
   the chain check and its `strict` / `warn` / `off` modes match the CLI,
   and each entry signature is verified separately so one bad entry is
   flagged instead of hiding the list. The chain anchor status comes from
   the chain check record the library saves; head expiry is not shown
   yet because the library does not expose it. Capabilities allow only
   those two commands and event listening; the CSP has no remote origins.
   Platform wiring is in `platform.rs` behind `cfg(target_os)`. Verified
   on the Linux build host: `tauri build` makes the release binary, a
   .deb, and an AppImage, and the window starts under Xvfb, syncs the
   official catalog in strict mode, and shows all entries verified and
   anchored. Not done: tray, settings view, entry page, `tensorseed gui`
   stub, deep link routing to entries, and Windows build checks. The
   updater plugin is not added; it lands in M3.6 with the updater key.
4. **M3.3 Pull.** Pull with progress, pause, resume, cancel; library view;
   job state shared with the CLI.
5. **M3.4 Seed.** Single seeder lock, in process engine, attach to a
   running `serve` through a local control endpoint; seeding controls and
   stats in window and tray.
6. **M3.5 Settings and HF login.** Editable settings writing the shared
   config; HF login, status, logout.
7. **M3.6 Packaging.** Linux .deb, .rpm, AppImage; Windows MSI and NSIS
   (unsigned); minisign signatures and checksums; updater artifacts,
   `.sig` files, and the `latest.json` feed on tensorseed.dev. Note from
   M3.2: the generated `.desktop` file has no `%u` in `Exec`, so installed
   packages need a desktop template for `tensorseed://` links. macOS stays
   a portability check only.
8. **M3.7 Release.** Smoke tests on Linux and Windows, docs and site page
   (including the SmartScreen note), CHANGELOG, 0.3.0 tag and launch.

## 7. Decisions

Recorded from the plan review. "Default" means the question was not
answered and the recommendation stands until revisited.

1. **macOS.** Designed for, not released in 0.3.0. Code stays portable and
   platform specifics are cfg gated, but 0.3.0 release targets are Linux
   and Windows only. SPEC 19 is unchanged on macOS. The signing and
   notarization path is later work (section 5).
2. **Windows signing.** Ship unsigned at first and document the
   SmartScreen prompt. Revisit Authenticode after launch.
3. **Windows installers.** Both MSI and NSIS.
4. **Updater.** Ship the Tauri in app updater in 0.3.0 with a new updater
   key, generated on the release machine (never the build host), and a
   static feed on tensorseed.dev (section 5, Updater).
5. **CLI bundling.** Default: Desktop packages bundle the CLI binary, so
   one install gives both; a dependency on the CLI package can replace it
   later where a package repository exists.
6. **Seeder model.** Default: Desktop attaches to a running `serve`, else
   runs its own engine behind a lock file (section 3, item 4).
7. **Repository layout.** `desktop/` and `ui/` live in this repository.
8. **Name and identifiers.** "Tensorseed Desktop", bundle id
   `dev.tensorseed.desktop`, and the `tensorseed://` URL scheme.
9. **Telemetry.** None, not even opt in. The update check is the only
   automatic network request the app makes beyond catalog sync.
10. **Linux minimum.** webkit2gtk-4.1: roughly Ubuntu 22.04, Debian 12,
    Fedora 36 or newer.
